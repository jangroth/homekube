## 065 — Hold Cilium at 1.20.1; kernel BTF is becoming a hard Cilium requirement that Raspberry Pi OS does not satisfy (2026-10-03)

**Area:** networking

**Decision:** Pinned `cilium_version: "1.20.1"` in `homekube-main/ansible/group_vars/all.yml` and disabled Renovate updates for the `cilium` dep (`enabled: false` packageRule in `homekube-main/renovate.json`) — the version is now held deliberately, not tracked. Accepted that this forgoes all future 1.20.x patches. Revisit in ~3 months (≈2026-01) or sooner if either escape route below opens. The proposed `socketLB.enabled: false` fix ([PR #23](https://github.com/jangroth/homekube-main/pull/23), [issue #51](https://github.com/jangroth/homekube/issues/51)) is rejected as a no-op.

**Rationale:** Cilium 1.20.2's agents never complete datapath initialisation on any node: `cil_sock4/6_connect`, `cil_sock4/6_post_bind`, `sendmsg`, `recvmsg`, `getpeername` all fail to load with `no BTF found for kernel version 6.18.29+rpt-rpi-2712: not supported`, and the orchestrator retries forever. Impact is worse than first recorded — CNI ADD is starved (`[PUT /endpoint/{id}][429] putEndpointIdTooManyRequests`, ~1234 occurrences over 25h), so **no new pod can get an endpoint on any node**, while existing pods survive on already-programmed rules. The agent reports `1/1 Running`/`Ready=True`/`RESTARTS 0` throughout, which is why this stayed invisible.

Root cause is [cilium/cilium#47737](https://github.com/cilium/cilium/pull/47737) (`bpf: use bpf_core_enum_value_exists() for HAVE_SET_RETVAL`), which replaced a compile-time `#ifdef HAVE_SET_RETVAL` in `bpf/include/bpf/helpers.h`'s `try_set_retval()` with a load-time CO-RE builtin — turning a build-time feature probe into a runtime BTF dependency. Verified per tag: 1.18.0–1.18.14 and 1.19.0–1.19.7 and 1.20.0–1.20.1 use the `#ifdef`; **1.19.8 and 1.20.2 use the CO-RE builtin**. It was backported to both maintained branches but kept off 1.18 ([#48405](https://github.com/cilium/cilium/pull/48405)). Upstream tracker: [cilium/cilium#48778](https://github.com/cilium/cilium/issues/48778), filed by another Pi 5 user on the same kernel.

BTF genuinely is absent on these kernels (this contradicts the premise recorded in `CHANGELOG.md` for 2026-10-02): no `/sys/kernel/btf/` on any of pi0–pi3, zero `DEBUG_INFO_BTF` entries in `bcm2712_defconfig`, and no `.BTF` section in any module of 6.18.39 or the staged 6.18.50 — so the pending reboot would not have helped. `CONFIG_DEBUG_INFO_BTF=y` has meanwhile appeared in Cilium's documented base requirements without ever being called out in an upgrade note.

1.20.1 is chosen over a 1.18.x downgrade (the only branch that is both safe *and* still patched) because it is one patch release back, is empirically known-good on these exact kernels, and 1.18 is the oldest maintained branch and will EOL first. Cilium's actual EOL dates could not be retrieved and are unknown.

**Trade-offs accepted:** The pin is frozen — the regression sits in the head of both maintained branches, so every future 1.19.x/1.20.x patch will carry it absent an upstream revert, and security patches will require re-evaluating this decision rather than a version bump. Renovate no longer reports Cilium releases at all, so new versions must be checked manually at revisit time. Maintainer position is that this will not be reverted (joestringer: *"I would not propose to change this for v1.20.x or later"*, and *"Realistically in the mid to longer term I would expect BTF to be a hard constraint... I don't see a way that Cilium could avoid that constraint"*), so **this is a deferral, not a fix — Cilium on stock RPi OS kernels is a platform-level risk to the CNI choice on a 6–12 month horizon.** Two escape routes exist, neither committed: (a) a pre-generated BTF blob dropped at one of the seven fallback paths `cilium/ebpf`'s `btf/kernel.go` already searches (`/boot/vmlinux-$(uname -r)`, `/lib/modules/%s/build/vmlinux`, `/usr/lib/debug/boot/vmlinux-%s`, …) — ~5.1 MB raw, mechanically sound and cheaper than the upstream thread assumes, but needs a `hostPath` mount into the agent and is unproven on a Pi 5; (b) Raspberry Pi shipping BTF, which [raspberrypi/linux#6622](https://github.com/raspberrypi/linux/issues/6622) suggests will not happen in-tree on size grounds (32 MB → 280 MB kernel; `DEBUG_INFO_REDUCED` is incompatible with BTF; `pahole` is absent from their toolchain), leaving a separate BTF package as the live but uncommitted option. There is no configuration escape hatch and none in flight: `btf/kernel.go` has no env-var or config override at `main`, and searches for external-BTF-path issues/PRs in both `cilium/cilium` and `cilium/ebpf` return nothing.
